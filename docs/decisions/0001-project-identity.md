# ADR 0001 — 프로젝트 식별자

- 상태: **구현 완료** (v0.3.0)
- 날짜: 2026-08-21
- 대상 릴리스: v0.3.0 — Project Relations

---

## 문제

DevTrail 은 프로젝트를 여러 이름으로 부르고 있고, 그 이름들이 서로 다를 수
있다. 관계를 만들려면 **무엇이 같은 프로젝트인지** 먼저 정해야 한다.

지금 코드에 실제로 존재하는 이름은 넷이다.

| 이름 | 어디서 오는가 | 누가 쓰는가 |
|---|---|---|
| **레포 키** | `github.project_groups` 의 키 | `anm.py:68` 자동 이동 규칙 · `augmentcmd.sh:220` 템플릿 선택창 |
| **섹션명** | `github.project_groups` 의 값 | `summary.sh.tmpl:43` PR 요약이 들어갈 `#### 제목` |
| **볼트 폴더명** | `프로젝트/` 아래 실제 폴더 | `Project doc.md:70` · `worklog` 스킬 |
| **표시 제목** | 사용자가 노트에 쓰는 것 | 어디서도 읽지 않음 |

`project_groups` 는 이미 **레포 키 → 섹션명** 매핑이다. 값이 키와 다를 수
있다 — `fe`/`be` 로 나뉜 레포를 한 섹션에 모으려고 만든 기능이다
(`summary.sh.tmpl:34` 가 `"acme-*"` 접두사 일치까지 지원한다).

**그래서 "새 canonical ID 를 도입하자"는 틀린 처방이다.** 이미 있는 것과
두 벌이 되어 반드시 갈라진다. 이 저장소는 같은 실수를 세 번 했다 —
경로 해석기 3개, 백업 12곳, `_ob_paths_json` 의 순서 의존.

## 지금 무엇이 깨져 있는가

1. **등록 경로가 `devtrail init` 뿐이다.**
   Obsidian 에서 `⌘⇧P` 로 만든 프로젝트는 `project_groups` 에 없다.
   그래서 개발일지·개발메모의 선택창에 안 나온다.

2. **개발일지는 프로젝트를 검색 가능한 관계로 남기지 않는다.**
   개발메모는 `project/<키>` 태그를 붙이는데(`Dev note.md:106`),
   개발일지는 `#### <섹션명>` 제목만 만든다(`Devlog.md:140`).
   같은 선택인데 한쪽만 관계가 된다.

3. **볼트 폴더명과 레포 키가 같다는 보장이 없다.**
   `anm.py:69` 는 `project/<레포키>` 태그를 `프로젝트/<레포키>` 폴더로
   보낸다. 폴더 이름이 다르면 노트가 없는 폴더로 간다.

## 결정

### D1. 정식 키는 `project_groups` 의 **키**다

관계를 만드는 모든 곳이 이 값을 쓴다.

```
#project/<키>          태그
project: <키>          frontmatter
프로젝트/<키>/          볼트 폴더
```

**섹션명(값)은 표시 전용이다.** PR 요약의 `####` 제목에만 쓴다.
관계 키로 쓰지 않는다 — 여러 레포가 한 섹션을 공유할 수 있으므로
값에서 키를 되찾을 수 없다.

**근거**: 자동 이동 규칙(`anm.py`)이 이미 키를 쓴다. 여기를 바꾸면
기존 사용자의 라우팅이 전부 깨진다.

### D1a. wildcard 항목은 프로젝트가 아니다

`project_groups` 의 키에는 `"acme-*"` 같은 접두사 규칙이 들어갈 수 있다
(`summary.sh.tmpl:34`). 그건 **PR 요약 섹션을 찾는 매칭 규칙**이지
프로젝트가 아니다.

> `project_groups` 의 wildcard 항목은 프로젝트가 아니라 PR 섹션 매칭
> 규칙이다. `devtrail project add` 는 wildcard 를 거부하며, 실제
> 프로젝트 관계 · 태그 · 폴더에는 exact key 만 쓴다. wildcard 규칙의
> 장기 저장 위치와 기존 설정 마이그레이션은 별도 결정으로 다룬다.

**이건 v0.3 설계 문제가 아니라 v0.2.0 의 실제 결함이다.** 확인한 것:

```
$ python3 lib/gen/anm.py … (project_groups 에 "acme-*": "acme" 가 있을 때)
  폴더: 창기/개발/프로젝트/acme-*   태그: #project/acme-*
```

`*` 가 든 폴더로 보내는 라우팅 규칙이 만들어진다. `#project/acme-*` 는
Obsidian 태그로 만들 수 없으므로 **영원히 매치되지 않는 죽은 규칙**이다.
같은 값이 개발일지·개발메모의 프로젝트 선택창에도 항목으로 뜬다
(`augmentcmd.sh:220`).

즉 wildcard 키가 **세 곳에서 실제 프로젝트로 오인된다**:
`anm.py`(라우팅) · `augmentcmd.sh`(선택창) · 그리고 앞으로 만들
`project add`.

**구현 첫 작업은 이 셋에서 wildcard 를 걸러내는 것이다.** 설정은
그대로 두고 읽는 쪽에서 거른다 — 사용자의 `acme-*` 설정은 PR 요약에서
계속 동작해야 한다.

### D2. 볼트 폴더명 = 키

`프로젝트/<키>` 로 고정한다. `anm.py:69` 가 이미 그렇게 가정하고 있다.

사용자가 폴더를 손으로 다른 이름으로 만들었다면 **그건 DevTrail 이
관리하는 프로젝트가 아니다.** `devtrail doctor` 가 알려주되 강제로
옮기지 않는다.

> ⚠️ 키에는 파일명에 못 쓰는 문자가 들어갈 수 있다(`/`, `:` 등).
> GitHub 레포명은 `[A-Za-z0-9._-]` 만 허용하므로 실무상 안전하지만,
> 손으로 추가하는 경로가 생기므로 검증이 필요하다.

### D3. 키의 규칙

```
[A-Za-z0-9._-]+      길이 1~64
대소문자를 구분한다   (GitHub 레포명이 그렇다)
```

`devtrail project add` 가 이 규칙으로 검증한다.

### D4. 쓰기 경로를 하나 추가한다

```bash
devtrail project add <키> [--section <섹션명>]
devtrail project list
```

하는 일:
1. `project_groups` 에 등록 (섹션명 생략 시 키와 동일)
2. `프로젝트/<키>/` 골격 생성 (`augment` 와 같은 방식, 없는 것만)
3. 경로 맵 갱신 — 템플릿 선택창이 즉시 반영된다

**Obsidian `⌘⇧P` 는 그대로 둔다.** 다만 마지막에
"`devtrail project add <이름>` 을 실행하세요" 를 안내한다.
Templater 는 셸을 부를 수 없으므로 자동화할 수 없다.

#### 기존 폴더를 만났을 때

DevTrail 의 안전 계약을 그대로 따른다 — **기본 dry-run · 없는 것만 보강 ·
기존 파일 무수정.**

| 상황 | 동작 |
|---|---|
| 폴더 없음 | 등록 + 골격 생성 |
| 폴더는 있고 비었음 | 등록 + 없는 골격만 보강 |
| README·노트가 있음 | **등록만.** 기존 파일을 절대 고치지 않는다 |
| `docs/` 가 일부만 있음 | 없는 하위 폴더만 만든다 |
| 이미 등록된 키 | 아무것도 하지 않고 그렇다고 말한다 |

**실패 시 롤백**: 설정 쓰기와 폴더 생성은 하나의 저널 작업으로 묶는다
(`jr_begin project-add`). 어느 쪽이 실패해도 `devtrail undo` 로
되돌아간다. 설정만 바뀌고 폴더가 없거나 그 반대인 상태를 남기지 않는다.

### D5. 개발일지가 관계를 남긴다

지금 (`Devlog.md:140`):
```
#### myapp
- 
```

바꿀 모습:
```
#### myapp
> [[프로젝트/myapp/README|myapp]]
- 
```
그리고 frontmatter 에 `projects: [myapp, other]`.

> 제목은 **섹션**, 링크와 frontmatter 는 **키**다. 둘이 다를 수 있다 —
> 자세한 것은 D5a.

**단수 `project:` 를 쓰지 않는다.** 하루에 여러 프로젝트를 다루므로
일지 전체를 하나에 귀속시킬 수 없다. 개발메모는 노트 하나가 프로젝트
하나에 속하므로 단수 `project:` 를 유지한다.

### D5a. 경로 맵이 키와 섹션을 함께 내려보낸다

**리뷰 2회차에서 발견한 것. wildcard 보다 더 직접적인 계약 충돌이다.**

지금 경로 맵은 `project_groups` 의 **키만** 배열로 내려보낸다
(`augmentcmd.sh:220`). 개발일지는 그 값을 그대로 `####` 제목으로 만들고
(`Devlog.md:100`), `summary.sh` 는 **값**으로 매핑한 섹션을 찾는다
(`summary.sh.tmpl:43`).

재현:

```
설정   { "acme-fe": "acme", "acme-be": "acme" }
선택창 ["acme-be", "acme-fe"]          ← 키만 전달됨
제목   #### acme-fe                     ← 키로 만들어짐
summary 가 찾는 것  #### acme            ← 값으로 매핑
결과   PR #123: 'acme' 섹션 없음 - 건너뜀
```

**`--section` 을 쓰는 순간 D4 의 「여러 레포 → 한 섹션」이 깨진다.**
그리고 이건 v0.3 문제가 아니라 **v0.2.0 결함**이다. `summary.sh.tmpl:32-34`
가 지원한다고 적어둔 그룹핑이 끝까지 동작하지 않는다.

> `init` 은 항등 매핑(`{name: name}`)을 만들므로 **기본 설정은 안전하다.**
> 사용자가 그룹핑하려고 값을 고치는 순간 깨진다.

#### 계약

경로 맵이 **관계를 구조로** 내려보낸다.

```json
"projects":         ["acme-fe", "acme-be", "myapp"],
"project_sections": { "acme-fe": "acme", "acme-be": "acme", "myapp": "myapp" }
```

> ⚠️ 처음에는 `[{key, section}]` 객체 배열로 정했다가 **D7 에서 폐기했다.**
> `projects` 의 타입을 바꾸면 옛 템플릿이 태그와 파일명을 오염시킨다.
> 키를 **더하는** 방식으로 바꿨다.

각 소비자가 무엇을 쓰는지 정한다.

| 소비자 | 쓰는 것 |
|---|---|
| 선택창 (개발일지·개발메모) | `key` — 정식 키를 고른다 |
| 개발일지 frontmatter | `key` — `projects: [acme-fe, acme-be]` |
| 개발일지 `####` 제목 | `section` — **중복 제거**. `#### acme` 하나 |
| 프로젝트 링크 | `key` — 섹션 아래에 키별 링크 |
| `summary.sh` | `section` — 지금 그대로. 안전하게 삽입된다 |
| 자동 이동 규칙 | `key` — wildcard 제외 (D1a) |

제목이 섹션으로 합쳐지므로 개발일지는 이렇게 된다.

```markdown
#### acme
> [[프로젝트/acme-fe/README|acme-fe]] · [[프로젝트/acme-be/README|acme-be]]
- 
```

**관계 키(`key`)와 표시 섹션(`section`)을 분리한다는 D1 의 원칙은 맞았다.
다만 경로 맵과 템플릿까지 그 구조를 전달해야 성립한다.**

#### 호환

**D7 참조.** `projects` 의 타입은 바꾸지 않는다.

### D6. 프로젝트 골격의 단일 출처

지금 골격(`docs/` 8영역 + `worklogs/`)은 Templater 템플릿 안에만 있다
(`New project.md:77`). `project add` 도 같은 것을 만들어야 하는데, 둘이
각자 가지면 **반드시 갈라진다** — 이 저장소가 세 번 겪은 실패다.

선언을 데이터로 옮긴다:

```
preset/project-skeleton.json
{
  "docs": ["00-overview", "01-product", "02-domain", "03-architecture",
           "04-data", "05-infra", "06-compliance", "07-delivery"],
  "dirs": ["worklogs"]
}
```

- CLI 는 이 파일을 읽어 만든다
- 템플릿은 경로 맵(`_devtrail-paths.md`)을 통해 받는다
  — 이미 `naming` · `ns` 를 그렇게 내려보내고 있다
- 검사가 둘의 일치를 본다 (문서 배치 매핑 때와 같은 방식)

> ⚠️ `tree.json` 에 넣지 않는다. 거기는 **볼트 최상위 구조**를 정하는
> 곳이고, 프로젝트 골격은 프로젝트 폴더 **안**의 구조다. 층이 다르다.

## 마이그레이션

### 기존 설정

`project_groups` 의 의미는 바뀌지 않는다. **스키마 변경 없음.**

### 기존 노트

- 개발일지의 `#### <이름>` 제목은 **건드리지 않는다.**
  이름이 섹션명일 수도 키일 수도 있어 되찾을 수 없다.
  새로 만드는 일지부터 관계를 남긴다.
- 개발메모의 `project/<값>` 태그는 그대로 둔다.

### 볼트 폴더

키와 다른 이름의 프로젝트 폴더는 `devtrail doctor` 가 보고만 한다.

```
⚠️ 프로젝트 폴더 2개가 등록되지 않았습니다
     프로젝트/legacy-app  → devtrail project add legacy-app
```

## 리뷰에서 정해진 것

### Q1. `--section` 은 wildcard 를 받지 않는다

`devtrail project add` 는 **구체적인 프로젝트 키만** 등록한다.
`--section` 은 값(표시명)만 받는다.

여러 레포를 한 섹션에 모으려면 **각각을 exact key 로 등록하고 같은
section 값을 주면 된다.**

```bash
devtrail project add acme-fe --section acme
devtrail project add acme-be --section acme
```

이러면 라우팅도 선택창도 정상 동작한다. wildcard 는 그중 어느 것도
못 한다.

기존 wildcard 설정은 **PR 요약에서 계속 동작한다** — 읽는 쪽에서만
거른다. 장기 저장 위치는 별도 결정으로 다룬다.

### Q2. RepoDocs 는 자동 추론으로 잇지 않는다

`RepoDocs/<레포명>` 과 `프로젝트/<키>` 가 **정확히 같을 때만** 참조한다.
다르면 프로젝트 허브에 이렇게 표시한다:

```
연결되지 않은 RepoDocs: acme-frontend
  → 명시적 매핑이 필요합니다 (v0.4)
```

이름이 비슷하다고 잇지 않는다. 틀린 연결은 없는 연결보다 나쁘다.

`no_index: true` 와 RAG 제외는 **그대로 유지한다.** 거울 폴더를 RAG 에
넣으면 원본 레포 문서가 사용자 노트를 검색 결과에서 밀어낸다.

### Q3. 프로젝트 폴더의 수동 노트는 옮기지 않는다

`no_automove: true` 를 유지한다. 이게 의도다.

- 문서·worklog 템플릿이 **정해진 위치에 직접** 만든다
- 사용자가 손으로 만든 노트는 사용자가 관리한다

가이드에 이 규칙을 명시한다 — 지금은 "자동 이동에서 뺐습니다"까지만
적혀 있고 **누가 배치를 책임지는지**가 없다.

## 이 결정이 열어주는 것

계약이 확정되면 아래를 **같은 키 위에서** 만들 수 있다.

```
프로젝트 README (허브)
 ├─ 목표 / 다음 행동
 ├─ 설계안 · ADR · 요구사항     docs/<번호>-<영역>/   ← v0.2 에서 이미 고침
 ├─ worklog · 연결된 개발일지    #project/<키>
 ├─ 이슈 · PR                   project_groups
 ├─ 트러블슈팅                  #project/<키>
 └─ RepoDocs                    devtrail sync
```

## 회귀 테스트 (구현과 함께 들어간다)

계약이 지켜지는지 기계로 확인한다. 다섯 가지다.

| # | 설정 | 확인할 것 |
|---|---|---|
| 1 | `{myapp: myapp}` | 항등 매핑 — 키·섹션이 같고 지금과 동일하게 동작 |
| 2 | `{acme-fe: acme, acme-be: acme}` | 선택창에 키 2개 · 제목은 `#### acme` **하나** |
| 3 | 2번 상태 | frontmatter `projects: [acme-fe, acme-be]` — **exact key 만** |
| 4 | 2번 상태 | `summary` 가 `#### acme` 에 실제로 삽입한다 |
| 5 | `{acme-*: acme}` | 선택창·라우팅에서 **제외** · PR 요약에서는 **유지** |

5번이 D1a 와 D5a 를 동시에 지킨다 — wildcard 는 프로젝트가 아니지만
매칭 규칙으로는 살아 있어야 한다.

## 릴리스 분리

처음에는 두 결함을 함께 v0.2.1 로 빼려 했으나, **D5a 는 hotfix 가 아니다.**

경로 맵(`_devtrail-paths.md`)은 매번 덮어쓰지만 **템플릿은 사용자 볼트에
이미 복사돼 있고 덮어쓰지 않는다**(`templates.sh:34` — 같은 이름이면
건너뛴다). 경로 맵 포맷만 바꾸면 **새 데이터 + 옛 템플릿** 조합이 생긴다:

```
옛 데이터 ["acme-fe"]                    → #### acme-fe
새 데이터 [{key:"acme-fe",section:...}]  → #### [object Object]
```

일부 사용자만 고쳐지고 일부는 더 망가진다.

| 릴리스 | 포함 | 이유 |
|---|---|---|
| **v0.2.1** | wildcard 를 라우팅·선택창에서 제외 (D1a) | 문자열 배열 계약을 보존하며 죽은 규칙만 제거 |
| **v0.3.0** | `{key, section}` 구조 · 템플릿 변경 · 호환 처리 (D5a) | 설치된 사용자 템플릿과 경로 맵 포맷까지 바꾸는 계약 변경 |

### v0.2.1 — 완료

- `anm.py` · `augmentcmd.sh` 에서 wildcard 를 거른다
- `summary.sh` 는 그대로 — wildcard 가 계속 동작한다
- 회귀 테스트 14개 (`tests/test-project-keys.sh`)

### D7. 호환 — 경로 맵은 키를 '더하고', 바꾸지 않는다

D5a 를 구현하려면 옛 경로 맵과 옛 템플릿을 어떻게 다룰지 정해야 한다.
처음 세운 후보 셋은 **전부 무효였다.**

| 후보 | 왜 무효인가 |
|---|---|
| `dtProjects()` 가 두 포맷 흡수 | 헬퍼는 **템플릿 안에 복사**돼 있다. 옛 볼트에는 흡수할 코드 자체가 없다 |
| 경로 맵에 `schema` 필드 + 분기 | 같은 이유. 분기 코드가 옛 템플릿에 없다 |
| `--refresh-templates` | 갱신 전까지 깨진 채고, 사용자가 고친 템플릿을 덮어쓴다 |

셋 다 **"옛 템플릿이 새 데이터를 보는 순간"** 을 막지 못한다. 문제를 잘못
세웠다 — 고칠 곳은 템플릿이 아니라 **데이터 쪽**이다.

#### 깨지는 정도 (확인함)

옛 템플릿에 객체 배열을 주면 표시만 깨지는 게 아니다.

```
개발일지  suggester 항목      → [object Object]
개발메모  tags: project/${p}  → project/[object Object]   ← 태그 오염
회고      파일명 parts        → [object Object]_2026-08_회고  ← 파일명 오염
```

#### 결정

**`projects` 는 문자열 배열 그대로 두고, 관계는 새 키로 더한다.**

```json
{
  "projects": ["acme-fe", "acme-be"],
  "project_sections": { "acme-fe": "acme", "acme-be": "acme" }
}
```

- **옛 템플릿**: `projects` 만 읽는다 → 지금과 100% 동일하게 동작
- **새 템플릿**: 둘 다 읽는다 → 섹션 중복 제거

> JSON 에 키를 **더하는 것**은 기존 소비자를 깨지 않는다.
> **바꾸는 것**만 깬다. D5a 의 `{key, section}` 객체 배열은 폐기한다.

#### 기존 사용자에게 새 템플릿을 주는 법

새 템플릿은 이름이 같아 설치되지 않는다(`templates.sh:34` — 기존 유지).
그래서 기존 사용자는 안 깨지지만 새 기능도 못 받는다.

**덮어쓰지 않는다. 알리고 사용자가 정한다.**

```
$ devtrail obsidian
▶ 노트 템플릿
✅ 템플릿 3개 설치 (기존 유지 18개)
⚠️ 개발일지양식.md 가 구버전입니다 — 프로젝트 섹션 묶기가 동작하지 않습니다
   내용 비교:  devtrail template diff 개발일지양식.md
   바꾸기:     devtrail template update 개발일지양식.md
```

- 자동으로 바꾸지 않는다
- 무엇이 다른지 먼저 볼 수 있다
- 바꾸면 저널에 남아 `devtrail undo` 로 되돌아간다

**판별 방법**: 헬퍼 헤더에 버전 표시를 넣는다.

```js
// ── DevTrail 공통 헬퍼 v2 ──
```

설치된 파일에 그 표시가 없으면 구버전이다. 사용자가 헤더를 지웠다면
구버전으로 보고 알리기만 한다 — 틀린 알림이 조용한 오작동보다 낫다.
